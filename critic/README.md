# critic

A Claude Code plugin for multi-reviewer fiction critique. The plugin orchestrates parallel reviews from Claude (as a subagent inside cowork), Codex (via the Codex CLI), and the [Pi harness](https://pi.dev) — then cross-reviews, synthesizes, and saves to your vault.

## How it works

Two layers:

- **A thin Go MCP server** that does file I/O on your vault, manages review files, loads prompt templates, and invokes the Codex and Pi CLIs.
- **Skills (markdown files in `skills/`)** that the orchestrating Claude in cowork follows. The skills compose prompts, spawn Claude subagents via the `Task` tool, and call MCP tools for everything else.

Claude work happens inside the cowork session (as subagents). External harnesses (Codex, Pi) are reached through the MCP server. The server keeps state for Codex and Pi sessions so cross-review can resume them.

## Architecture

```
       cowork session (Claude)
              │
   ┌──────────┼──────────┐
   │          │          │
   ▼          ▼          ▼
 Task     invoke-codex  invoke-pi      ← MCP tools
  │          │          │
  ▼          ▼          ▼
Claude     Codex      Pi
subagent   CLI        CLI
```

- **Claude** runs as a Task subagent inside cowork. No external process. Review and rejection-pass happen in a single subagent for true context continuity. Cross-review is a second subagent that receives the prior review verbatim.
- **Codex** is the official `codex` CLI authenticated via your ChatGPT subscription. The server wraps it and maintains session IDs for cross-review resume.
- **Pi** is the [pi harness](https://pi.dev) — a unified CLI that fronts multiple providers (anthropic, openai, google). The server wraps it the same way as Codex. The manuscript skill picks a model interactively using `pi --list-models`.

## Vault structure

```
vault/
  story/                 — one markdown file per chapter, sorted by filename
  world/                 — world-building notes (optional)
  plot/                  — plot outlines and arcs (optional)
  summary/               — chapter summaries (generated by /critic:summarize)
  review/                — saved reviews (numbered: 003-manuscript-critic-...)
  prompts/               — per-vault prompt overrides (optional)
  stage.md               — current draft stage (optional but highly recommended; calibrates reviewers)
  style.md               — style guide (optional; passed to reviewers)
  issues.md              — deferred issues (managed by /critic:rebuttal)
```

No frontmatter required. All files are read as plain text. Chapter files in `story/` should sort by filename (zero-pad numbers: `chapter-01.md`, not `chapter-1.md`).

## Installation

### Prerequisites

- [Claude Code](https://claude.com/claude-code) 1.0.33+
- Go 1.21+ to build the server
- [Codex CLI](https://developers.openai.com/codex/) authenticated with your ChatGPT subscription (`codex login`)
- [Pi CLI](https://pi.dev) installed and authenticated (`pi` once to set up the provider you want)

### Build and load

```bash
cd critic/server
go build -o ../bin/critic .

# Development load
claude --plugin-dir /path/to/critic
```

### Configure

```bash
/critic:settings vault_path /path/to/vault
/critic:settings pi_provider google      # or anthropic / openai
/critic:settings pi_model gemini-2.5-pro # optional; defaults to provider default
/critic:settings codex_enabled true      # default true
/critic:settings pi_enabled true         # default true
```

Settings are stored in the plugin data directory and persist across sessions. Defaults live in `config.yaml`; the settings skill overrides them.

Claude is always available — it runs as a subagent inside cowork. There's nothing to configure for Claude; its model is whatever cowork is running on.

## Skills

### `/critic:manuscript`

The primary workflow. Interactive setup, then runs straight through:

1. **Setup** — asks which reviewers to enable, which Pi model to use (`pi-list-models`), and which steps to run (rejection pass / adversarial pass / cross-review / synthesis / save).
2. **Execution** — independent reviews in parallel (Claude review + rejection in one subagent, Codex and Pi in parallel invoke calls), optional Pi adversarial pass, optional cross-review matrix (each reviewer rebuts both others), optional synthesis, save.

Cross-review is a full matrix: each of the three primary reviewers sees both counterparts' reviews when generating their rebuttal. Sessions are maintained for Codex and Pi (real resume via session ID) and emulated for Claude (the next subagent receives its prior review verbatim).

Saved review file structure:

```
review/NNN-manuscript-critic-YYYY-MM-DD-HHMMSS.md

  [synthesis with ISSUE-NNN-NN ids, the human-readable report]

  <!-- RAW AGENT OUTPUTS BELOW — NOT INCLUDED IN FUTURE REVIEW CONTEXT -->

  # Claude Review
  # Claude Rejection Pass
  # Codex Review
  # Pi Review
  # Pi Adversarial Pass
  # Claude Cross-Review Rebuttal
  # Cross-Review (Codex + Pi)
```

Future reviews see only the synthesis (above the sentinel) so feedback doesn't compound endlessly.

### `/critic:review <chapter>`

Chapter-level review with four role lenses (analytical, immersive, structural, adversarial). Same shape as the manuscript skill, scoped to one chapter. Non-interactive.

### `/critic:extract <chapter>`

Reads a chapter and diffs the asserted facts against `world/`. Reports new facts, confirmed facts, and contradictions. Interactive — proposes canon updates for your approval.

### `/critic:downstream <chapter>`

Assesses what breaks in subsequent chapters after editing the given chapter. Reads from the edited chapter through end-of-manuscript and flags continuity issues, invalidated setups, stale dialogue, timeline errors.

### `/critic:rebuttal <issue-id>`

Conversational. For a flagged issue, you can:
- **Rebut** — articulate why the issue isn't real; the rebuttal is added as an Obsidian callout in the review file. Future reviewers respect it.
- **Defer** — move the issue to `issues.md` for later. Future reviewers see it with instructions not to re-raise unless escalated.
- **Accept** — agree and fix it yourself.

### `/critic:assess <issue-id> [question]`

Deep-dive on a single review issue. The cowork session reads the chapter files directly and investigates: finds all occurrences of patterns, traces structural problems across the manuscript, optionally answers a follow-up question.

### `/critic:summarize`

Generates per-chapter summaries to `summary/`. Useful before a chapter review so the chapter reviewers can see prior chapters as compact summaries instead of full text.

### `/critic:consult <question>`

Quick second opinions from Codex and Pi on a focused question. Useful proactively when you want an outside read on something specific.

### `/critic:settings`

View and update plugin settings.

### `/critic:help`

Show the full skill reference.

## MCP tools (thin plumbing)

The server is small. These are everything it exposes:

| Tool | Purpose |
|------|---------|
| `invoke-codex` | Call Codex with system + user prompt. Optional `session_id` resume. Optional `include_manuscript_from` to append manuscript server-side. |
| `invoke-pi` | Same shape for Pi. Optional `provider` / `model` overrides (new sessions only). |
| `pi-list-models` | Wraps `pi --list-models`. Used by the manuscript skill to populate the model picker. |
| `get-prompt` | Load a prompt template. Resolution: `<vault>/prompts/<name>` > `$CLAUDE_PLUGIN_ROOT/prompts/<name>` > embedded. Optional template vars (Go `text/template`). |
| `next-review-number` | Global review counter. |
| `stage-review-part`, `assemble-review`, `save-review` | Review file assembly. |
| `read-issue`, `add-rebuttal` | Issue management within review files. |
| `read-issues`, `append-issue` | `issues.md` (deferred issues) management. |
| `list-chapters`, `summarize-chapter`, `write-summary` | Vault convenience tools. |
| `read-settings`, `write-setting` | Plugin settings. |
| `update-memory` | Legacy reviewer memory hook (not currently used). |

The orchestrating Claude composes prompts (via `get-prompt`), inlines the user-supplied context, and dispatches to the right place — either `invoke-*` for external harnesses or `Task` for subagents.

## Prompt overrides

All prompts ship inside the binary (`server/prompts/*.md`, embedded via `go:embed`). To customize, copy a prompt file to `<vault>/prompts/<name>.md` and edit. Resolution order on each call:

1. `<vault>/prompts/<name>.md` — per-project author override
2. `$CLAUDE_PLUGIN_ROOT/prompts/<name>.md` — plugin-level override
3. Embedded default — compiled into the binary

Templated prompts use Go `text/template` syntax:

| File | Variables |
|------|-----------|
| `review-base.md` | `{{.Role}}`, `{{.MaxIssues}}` |
| `cross-review.md` | `{{.MaxNewIssues}}` |
| `synthesis.md` | `{{.ReviewNum}}` (zero-padded to 3 digits) |
| (all others) | None |

## Review file format

- Filenames: `NNN-prefix-YYYY-MM-DD-HHMMSS.md` with a global counter across all review types.
- Issue IDs: `ISSUE-NNN-NN` where `NNN` matches the review number; the second segment is a sequential counter across the whole document (not reset per section).
- Sentinel `<!-- RAW AGENT OUTPUTS BELOW — NOT INCLUDED IN FUTURE REVIEW CONTEXT -->` splits the synthesis (above) from raw agent outputs (below). Future reviews see only the synthesis.
- Author rebuttals are added as Obsidian callouts inline after the issue they address.

## Reviewer framing

All reviewers operate as **publishing consultants** advising a literary agent who already represents the author. The framing:

- The agent has already decided to represent the author. The reviewer's job is to advise on whether the project is on track to sell to a major publisher.
- Surface issues (typos, minor style slips) are explicitly out of scope. Focus is on structural integrity, narrative momentum, character work, voice, premise delivery.
- Verdicts use four labels: On track / Worth fixing / Needs rethinking / Not working — all judged against the **foundations as built**, not against a finished book.
- The rejection pass (Claude) and adversarial pass (Pi) exist to counteract the constructive bias inherent to alignment-trained models.

### Calibrating reviewers to draft stage

Reviewers default to treating the manuscript as a finished product unless told otherwise. To prevent verdicts like "the arc doesn't resolve" when you've only written act 1, maintain a `stage.md` file at the vault root:

```markdown
# Current Stage

This is approximately 3/4 of the first act of a planned three-act novel.
Target final length: ~120,000 words. Current: ~30,000 words.

What this draft is currently trying to do:
- Establish the central mystery
- Develop the Henry/Luma relationship
- Set up the financial pressure

NOT yet attempted, by design:
- Resolution of any major thread
- Mid-book reversals
- Character arcs completing

Looking for feedback on:
- Whether the foundations support what's coming
- Issues that will compound if not addressed now
```

The manuscript skill injects this as `=== CURRENT DRAFT STAGE ===` at the top of every reviewer's prompt. Reviewers are instructed to treat it as authoritative and calibrate against it — they won't flag missing elements you haven't attempted.

Edit the framing in `prompts/agent-framing.md` and `prompts/manuscript.md` if you want a different stance.
